Homework 02

From Wallet Seed to Ethereum Address

Hashing, Key Derivation and Cryptographic Primitives

An exploration of the cryptographic standards behind Ethereum wallets, from mnemonic phrases to checksummed addresses, including statistical properties.

1. The Ethereum Wallet Cryptographic Pipeline

The generation of an Ethereum address from an initial human-readable mnemonic seed follows a strictly deterministic, multi-stage derivation sequence:

Mnemonic Phrase (12 or 24 English words) ↓ [BIP-39: PBKDF2 with HMAC-SHA512, 2048 rounds, salt="mnemonic"+passphrase] Binary Seed (512-bit master entropy) ↓ [BIP-32 / BIP-44: Child Key Derivation path m/44'/60'/0'/0/0] Private Key (256-bit scalar integer, k) ↓ [secp256k1: Scalar Multiplication Q = k · G] Public Key (64-byte uncompressed coordinate pair (X, Y), excluding '0x04' prefix) ↓ [Keccak-256: Cryptographic Sponge Hash Function] Address Pre-image (256-bit hash digest) ↓ [Truncation: Discard top 12 bytes, retain lower 20 bytes (160 bits)] Raw Ethereum Address (40-character hexadecimal string) ↓ [EIP-55: Mixed-Case Capitalization Checksum] Checksummed Ethereum Address (e.g., 0x5aAeb6053F3E94C9b9A09f33669435E7Ef1BeAed)

Roles and Purposes of Core Standards

  • BIP-39: Encodes 128–256 bits of CSPRNG entropy into 12–24 dictionary words with a built-in checksum. Applies PBKDF2 with HMAC-SHA512 over 2,048 rounds to stretch the phrase into a 512-bit binary seed.
  • BIP-32 & BIP-44: Creates a Hierarchical Deterministic (HD) key tree allowing infinite child key derivations from a single seed. Uses the Ethereum mainnet path: m / 44' / 60' / 0' / 0 / 0.
  • secp256k1: Koblitz curve over prime field F_p (y^2 = x^3 + 7 mod p) mapping private key k to public key Q = k · G via the intractable Elliptic Curve Discrete Logarithm Problem (ECDLP).
  • Keccak-256: Evaluates the 64-byte uncompressed (X, Y) coordinate point, stripping the first 12 bytes and retaining the lower 20 bytes (160 bits).
  • EIP-55: Mixed-case capitalization checksum encoding to detect accidental human transcription mistakes without altering payload length.

3. Chronological Context & Historical Evolution

1977
RSA: Landmark asymmetric cryptography based on prime integer factorization.
2001
SHA-2 (SHA-512): NIST standardization of iterative Merkle-Damgård compression.
2012
BIP-32: Pieter Wuille formalizes hierarchical deterministic derivation.
2013
BIP-39: Mnemonic phrases introduced for human-friendly wallet backups.
2014
BIP-44: Standardized multi-account derivation tree hierarchies.
2015
SHA-3: NIST standardization of the Keccak sponge function family.
2016
EIP-55: Vitalik Buterin introduces backward-compatible checksum encoding.
Technical Distinction: Keccak-256 vs NIST SHA3-256
Ethereum integrated Keccak in late 2014 before NIST completed the final specification in August 2015. During finalization, NIST changed the domain separation padding byte (0x06 for SHA3-256 vs 0x01 in original Keccak). Consequently, Ethereum's Keccak-256 produces completely distinct hash digests from NIST SHA3-256.

4. Multi-Primitive Security Trade-Offs

  • Usability vs Key Management: Humans cannot reliably remember 256-bit raw hex keys. BIP-39 and BIP-44 allow a single mnemonic phrase to manage an entire account tree.
  • Authentication vs Storage: Digital signatures require public keys with elliptic group structures, but storing 64 bytes per account would bloat the Ethereum state trie. Keccak-256 compresses this to 20 bytes, saving 68% of storage.
  • Fault Tolerance: Blockchain transactions are irreversible. EIP-55 introduces client-side error detection without requiring additional byte overhead on-chain.

5. Statistical Analysis & Security Bounds

  • Strict Avalanche Criterion (SAC): The outputs of HMAC-SHA512 and Keccak-256 exhibit independent bit-flip probabilities (P ≈ 0.5), ensuring pseudo-random output distributions across the derived keys.
  • Birthday Paradox & Collision Resistance: Truncating Keccak-256 to 160 bits yields a collision resistance bound of 2^80 operations. In distributed ledger architecture, 2^80 operations remains computationally unfeasible while saving storage.
  • EIP-55 Typo Detection Reliability: In an address with m alphabetic characters, each character acts as an independent binomial trial. For an address containing 15 letters:
    P(undetected typo) ≈ 2^(-15) ≈ 0.003% &implies; 99.997% Error Detection Rate
